# Заказы и выручка по артикулам за день

Скрипт читает выгрузку заказов `sales.csv` и пишет `daily_by_sku.csv` — одна строка на пару «артикул — день»:

| колонка | что это |
|---|---|
| `sku` | артикул |
| `order_date` | день, ГГГГ-ММ-ДД |
| `orders` | сколько заказов было за день, отменённые тоже считаются |
| `revenue` | выручка за день в рублях: сумма `quantity × price` только по выкупленным (`delivered`) заказам |

Строки отсортированы по артикулу, внутри артикула — по дате.

## Как запустить

Нужен Python 3.8 или новее. Для основного скрипта ничего ставить не нужно, хватает стандартной библиотеки.

1. Положите `sales.csv` в корень репозитория (в git его нет).
2. Запустите:

   ```bash
   python daily_by_sku.py
   ```

3. Результат появится в `daily_by_sku.csv` рядом со скриптом. В консоль выводится короткая сводка: сколько строк прочитано, сколько дублей удалено и общая выручка.

Пути можно передать явно: `python daily_by_sku.py путь/к/sales.csv путь/к/результату.csv`.

Готовый результат по присланной выгрузке уже лежит в репозитории: `daily_by_sku.csv`.

## Как проверял, что расчёт верный

1. **Тесты на игрушечной выгрузке** (`test_daily_by_sku.py`): несколько строк, ответ для которых я посчитал вручную. Там есть дубль, отменённый заказ, все варианты опечаток в статусах, отмена без количества и проверка сортировки. Отдельно проверяется, что скрипт падает на данных, которые нельзя исправить однозначно. Запуск: `python -m unittest -v`.
2. **Независимый пересчёт через pandas** (`check.py`). Тот же отчёт считается другим способом: удаляются полные дубли строк, затем `groupby`. Результат сравнивается с `daily_by_sku.csv` построчно. Чтобы убедиться, что сверка действительно ловит ошибки, я поменял одну цифру в результате — `check.py` упал. Запуск:

   ```bash
   pip install -r requirements-check.txt
   python check.py
   ```

3. **Ручная проверка одной строки** через `grep`/`awk` по сырому файлу: UYT-0001 за 2026-08-17 — 28 заказов, 27 650 ₽, совпадает с отчётом.

## Проблемы в данных и что я с ними сделал

| проблема | сколько | решение |
|---|---|---|
| Дубли строк | 60 заказов встречаются дважды, все копии совпадают по всем полям | Заказ считается один раз (ключ — `order_id`). Если бы копии различались, скрипт остановился бы с ошибкой: молча выбирать одну из них нельзя |
| Статус в разном регистре и с пробелом в конце: `Delivered`, `DELIVERED`, `delivered `, `Cancelled`, `CANCELLED` | 32 строки | Убираю пробелы по краям и привожу к нижнему регистру |
| Опечатка `canceled` вместо `cancelled` | 3 строки | Считаю отменой |
| Пустое `quantity` | 4 строки, все — отменённые заказы | В `orders` заказ учитывается, на выручку не влияет: отменённые в неё не входят. Если пустое количество встретится у выкупленного заказа, скрипт остановится с ошибкой |
| У UYT-0003 нет ни одного заказа 8, 9 и 10 сентября, хотя обычно их около 30 в день. Общее число заказов за эти дни тоже ниже | 3 дня | Данные не исправлял, придумывать их нельзя. Строк UYT-0003 за эти дни в отчёте нет. Похоже, товара не было в наличии или строки потерялись при выгрузке — стоит уточнить у владельца данных |

Что ещё проверил — тут проблем нет: у всех строк 6 полей; все даты корректные; артикулы без опечаток (12 штук); цена у каждого артикула одна и та же за весь период; `order_id` — числа без пропусков.

Любой другой неизвестный статус (например, `returned`) тоже останавливает скрипт с ошибкой и номером строки. Иначе такие заказы незаметно пропали бы из выручки.

## В чём не уверен

- **`canceled` = отмена.** Это очевидная опечатка, но формально такого статуса в описании нет.
- **Дни без заказов в отчёт не попадают.** Если по артикулу за день не было ни одного заказа, строки с нулями нет: 631 строка вместо 12 × 56 = 672. Если нужна полная сетка с нулями, это легко добавить.
- **Выручка привязана к дате заказа.** Даты выкупа в выгрузке нет, поэтому заказ, выкупленный позже, всё равно попадает в выручку дня оформления.
- **Цены целые, в рублях.** Если в выгрузке появятся копейки (`1490.50`), скрипт упадёт, а не округлит молча. Тогда нужно перейти на `Decimal`.
- **Пробел в данных UYT-0003 за 8–10 сентября** — см. выше. Причину по одной выгрузке не определить.
